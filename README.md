Поскольку мне нравится накручивать себе дополнительные задачи в подобных областях, эти проекты частично пересекаются с хобби. 3D-движок на `Tkinter`, собственный `BMP`-стек и дискретно-событийный движок вместо `AnyLogic` появились из любопытства, а не из требований задания. Порт `BigInteger` из OpenJDK потянул за собой исследование, которого в задании не было: выяснилось, что ключ к скорости — не только `pow`, но и `BitSieve`, сегментированное решето, отсеивающее кандидатов по малым простым до дорогого теста простоты. А в РГР по защите информации вместо разрешённого P2P-варианта захотелось собрать полноценный клиент-сервер с комнатами — с той разницей, что сервер не хранит пароль и не может расшифровать трафик, то есть получается настоящее сквозное шифрование, а не «шифрование до сервера».

### Симулятор логических схем (курсовой проект, монетизирован)
*2023*

Создал с нуля симулятор логических схем на `C#`/`Avalonia`.
- Реализовал визуальный редактор логических схем с собственным менеджером соединений.
- Впервые применил `mutex` из-за их **острой** необходимости: поток редактора и симулятора боролись за один и тот же контейнер, что было основным источником поломок ровно до того момента, как я познакомился с данной технологией против `race condition`.
- Настроил автоматический подсчёт версий (`билдов`).
- Разработал генератор `ER`-диаграмм на основе `C#`-рефлексии.
- Реализовал архитектуру по модели `MVVM` (Model → ModelView → View) с ациклическим графом зависимостей.
- Вёл разработку по модели `git-flow` (main, develop) с указанием версий (`билдов`).
- Проект продан 20+ студентам и сопровождался технической поддержкой до конца сессии.

### Компиляторный стек для Ascend NPU (Huawei)
*Декабрь 2025 – Июль 2026*  

Проект с ключевым заказчиком успешно завершён (релиз продукта), я отвечал за качество и производительность компилируемого кода. Дальнейшее трудоустройство в другие команды оказалось невозможным из-за отсутствия открытых вакансий.
- В пайплайне `TTIR` -> `TTADAPTER` (custom Triton-Ascend output for `AscendNPU-IR` backend) -> `HFusion` -> `HIVM` -> `BiSheng compiler backend`, отвечал за часть `AscendNPU-IR`: `HFusion`, `HIVM`.
- Обеспечиваю корпоративную безопасность и чистоту интеллектуальной собственности: чётко разделяю собственный код и код из приватных репозиториев.
- Создавал Merge Request’ы с исправлениями и новыми низкоуровневыми интринсиками (`intrinsics`) Ascend NPU, следуя внутренним стандартам оформления.
- Владею инструментарием `CANN Toolkit` (как внутренней сборкой, так и публичными релизами): понимаю назначение компонентов `ACL`, `op-compiler`, `ccec` и их взаимодействие при компиляции.
  * В качестве хобби, для упрощения отладки коммуникации с драйвером, сделал свою реализацию `CANN Toolkit`, полностью работающую с оригинальным `torch-npu`, на CPU, без утечек памяти: [от оригинального toolkit достались только заголовочные файлы](https://github.com/VectorASD/QuickStart/tree/master/llvm/my_acl).
- Координировал работу с командами через WeLink, выполнял задачи в рамках рабочего проекта, оперативно реагирую на запросы.
- Работал с тикетами: анализировал конфликтующие/устаревшие записи, готовил отчёты о проверках с заключениями о необходимости исправлений.

### Плагин чанкированной загрузки CLIP для ComfyUI (ComfyUI-VectorASD)
*Проект 2025 года, публичный релиз*  
Решил фундаментальную проблему нехватки видеопамяти при работе с большими текстовыми энкодерами в `Stable Diffusion`. Разработал плагин, который разбивает `CLIP`-модель на управляемые блоки, загружает их последовательно и освобождает `VRAM`, позволяя запускать пайплайн на картах с ограниченными ресурсами.

- Разработал собственный парсер и планировщик загрузки: алгоритм разбирает бинарный `safetensors`-формат, строит дерево тензоров через реконструированную логику (вдохновлённую минифицированным `JS` с `Hugging Face`) и автоматически нарезает модель на чанки с лимитом по `VRAM`, задаваемым пользователем. Никакой зависимости от `Google Protobuf` - только прямое чтение заголовков и работа со смещениями.
- Переписал внутренний цикл инференса `ComfyUI` так, чтобы он выполнял проход по блокам энкодера порциями, сохраняя промежуточное состояние (`эмбеддинги`, `attention mask`) и передавая его между загрузками. Это потребовало глубокой модификации `umt5_xxl` и аккуратного управления контекстом выполнения.
- Реализовал в `JavaScript`-расширении для графа узлов контролируемое изменение количества входов и динамическое переименование префиксов. Применил сортировку и лимитирование входов без потери состояния, демонстрируя работу с `DOM`-событиями и внутренним `API ComfyUI` на уровне, близком к разработке операторских панелей.
- Написал утилиты для анализа тензоров: расчёт `SHA-256`-дайджеста, ASCII-визуализация эмбеддингов (посимвольная и «прыжковая» на основе угловых смещений), глубокое сравнение сложных структур с защитой от циклов. Это показывает заботу о качестве и привычку к созданию прозрачных инструментов контроля.
- Впервые провёл глубокий разбор лицензий (`MIT`, `Apache 2.0`, неявные условия) при создании публичного проекта. Корректно оформил использование модифицированных компонентов `ComfyUI`, реконструированного кода и указал авторство, продемонстрировав ответственное отношение к интеллектуальной собственности.

[Репозиторий ComfyUI-VectorASD](https://github.com/VectorASD/ComfyUI-VectorASD)


### Утилиты для ComfyUI: мониторинг GPU и перехват фронтенда (ComfyUI-ASDUtils)
*Июль – Август 2026*

Создал набор инструментов, расширяющих среду `ComfyUI`, с фокусом на создание **операторских панелей реального времени** и **глубокую модификацию пользовательского интерфейса** через перехват внутренних механизмов. Проект родился из потребности контролировать аппаратные ресурсы прямо в графе узлов и обходить ограничения публичного `API` для реализации кастомных UI-решений.
- Разработал кастомный `DOM`-виджет на чистом `JavaScript`, встраиваемый в узел `ComfyUI`. Реализовал:
  * Создание контейнера с прогресс-барами и текстовыми индикаторами (GPU Utilization, VRAM Usage, Temperature) с нуля.
  * Динамическое обновление через подписку на серверные события (`api.addEventListener`) и изменение стилей (ширина, цвет) в реальном времени в зависимости от значений (норма/предупреждение/критично).
  * Привязку жизненного цикла монитора к узлу: создание при добавлении (`onAdded`), обновление параметров через `onWidgetChanged`, остановка при удалении (`onRemoved`), восстановление после переподключения сервера.
  * Адаптивную вёрстку: размеры виджета автоматически подстраиваются под размер узла с помощью `requestAnimationFrame` и расчёта отступов.
- Внедрил собственный middleware на стороне сервера (`aiohttp`) для перехвата ответов с фронтенд-ассетами (`/assets/promotionUtils-*.js`). Цель - в будущем инжектировать код для доступа к закрытым TypeScript-объектам (например, `widgetValueStore`), что требовало бы модификации скомпилированного TS в JS (`ComfyUI`-frontend).
- Реализовал разбор source map (формат `.js.map`) и декодирование `VLQ`-последовательностей для восстановления соответствия между минифицированным `JavaScript` и исходным `TypeScript`. Это позволило анализировать внутренние модули `ComfyUI` (например, `widgetValueStore.ts`) и готовить точечные инъекции. Несмотря на статус черновика, работа демонстрирует навыки реверс-инжиниринга и глубокого понимания принципов работы фронтенд-тулчейнов.
- Добавил загрузчики `CLIP` и `VAE` с возможностью принудительного выбора устройства (CPU/GPU), узел `PreviewAny` для отладки значений произвольных типов, а также провёл рефакторинг и унификацию кода с префиксом `ASD`.
- При создании монитора за основу был взят `AMD GPU Monitor` под `MIT`-лицензией; все модификации явно отмечены как производная работа с сохранением копирайтов оригинального автора. Собственные части проекта лицензированы под `Apache 2.0`, что демонстрирует ответственное отношение к интеллектуальной собственности.

[Репозиторий ComfyUI-ASDUtils](https://github.com/VectorASD/ComfyUI-ASDUtils)


### Деобфускатор JavaScript с полным конвейером анализа (deobfuscator)
*Декабрь 2025*

Разработал инструмент для восстановления читаемого кода из скриптов, защищённых виртуальной машиной и шифрованием строк. Проект объединяет парсинг `AST` (`Babel`), статический анализ типов, дешифрацию `RC4` и генерацию чистого `JavaScript`.
- Реализовал интеграцию с `Node.js` и `Babel` для парсинга и генерации кода, с кэшированием `AST` и возможностью загрузки исходных файлов из интернета.
- Создал анализатор `AST` на `Python`, собирающий статистику использования типов и их полей, с автоматическим расширением информации на основе иерархии наследования (`MRO`) из спецификации `Babel`.
- Разработал движок типизации: задал алиасы для каждого поля узлов, учёл множественное наследование (`supers`) и обнаружил скрытые поля, не задокументированные в Babel (например, `File`, `CommentBlock`).
- Реализовал деобфускатор вызовов `<некоторая функция>()`: декодировал `base64` (с swapcase) и применил `RC4` для расшифровки строк, восстановив исходные имена методов и свойств.
- Восстановил читаемый код виртуальной машины: заменил зашифрованные инструкции и модификаторы доступа на исходные, получив исполняемый `JavaScript` без обфускации.
- Внедрил механизм печати `AST` для отладки и визуализации структуры кода.

[Репозиторий деобфускатора (alpha)](https://github.com/VectorASD/deobfuscator)


### Криптографическая буферизация с цепочечным шифрованием (lab2buffers)
*Сентябрь 2024*

Реализовал потоковую обработку криптографических примитивов с минимальным расходом оперативной памяти. Позволяет комбинировать блочные шифры и хэш-функции в произвольные цепочки без загрузки всего файла.

- Обеспечил совместимость с стандартными файловыми объектами `Python` (`IOBase`, `BytesIO`), что позволяет применять цепочки к любым источникам данных «на лету».

### Информатизация предприятий
*7 – 14 октября 2025 (дополнено 4 декабря 2025)*

Проектирование реляционных баз данных и разработка запросов на языке `SQL` / `PL/SQL` (СУБД `Oracle`). Работа охватывает полный цикл: от построения `ER`-диаграмм и ограничений целостности до аналитики на основе оконных функций и написания триггеров для реализации специфичной бизнес-логики.

- **Базовые и сложные запросы (`SELECT`):** фильтрация, сортировка, агрегация (`GROUP BY`, `HAVING`), конкатенация строк (`||`, `CONCAT`) и работа с датами. Реализовал вложенные и коррелированные подзапросы для поиска данных со сложными условиями (например, отклонение от среднего оклада или поиск сотрудников, нанятых раньше своих менеджеров).
- **Соединения (`JOIN`):** использовал `INNER` и `LEFT` соединения, включая самосоединение (`self-join`) таблицы `EMPLOYEES` для вывода иерархии «сотрудник — руководитель». Связывал данные через промежуточные таблицы (`EMPLOYEES` → `DEPARTMENTS` → `LOCATIONS` → `COUNTRIES`).
- **Модификация данных (`DML`):** выполнял `INSERT`, `UPDATE` и `CREATE TABLE AS SELECT` (CTAS). Применял скалярные подзапросы внутри `UPDATE` для пересчёта значений на основе связанных таблиц (например, установка зарплаты на основе минимума для должности).
- **Оконные функции и аналитика:** рассчитывал ранги (`RANK`, `DENSE_RANK`, `ROW_NUMBER`), доли в общем фонде (`SUM() OVER`), разбиение на квартили (`NTILE`) и поиск «соседей» по хронологии (`LAG`, `LEAD`). Для статистического анализа взаимосвязи зарплаты и года найма применил ковариацию (`COVAR_SAMP`) и корреляцию (`CORR`) с разбивкой по `PARTITION BY`.
- **Проектирование БД и `PL/SQL` (РГЗ):** спроектировал `ER`-диаграмму для предметной области «Ремонт радиоаппаратуры» (`app.erdlab.io`), реализовал `DDL`-скрипты с ограничениями `FOREIGN KEY` (связи `M:1`). Для эмуляции `AUTO_INCREMENT` написал `CREATE SEQUENCE` и `BEFORE INSERT`-триггеры.
- **Обход ограничений Oracle:** столкнулся с ошибкой `mutating table` (ORA-04091) при попытке читать таблицу внутри триггера `BEFORE INSERT`. Решил проблему через вынос логики проверки в функцию с `PRAGMA AUTONOMOUS_TRANSACTION` (автономная транзакция). Исследовал поведение `NEXTVAL` при откате транзакции (`ROLLBACK`) и убедился, что значения последовательностей не откатываются — это не баг, а фича СУБД.

### Прикладная стеганография
*17 февраля – 7 мая 2026*

Самая тяжёлая дисциплина за всё время — и не из-за алгоритмов, а из-за контекста: она шла параллельно с основной работой над `AscendNPU-IR` в Huawei, где времени на что-то кроме рабочих задач почти не оставалось. Другие дисциплины в этот промежуток не брались. Зато именно здесь появились термины `растр`, `bpp`, `PSNR` и `RDH`, которые потом стали основой для НИР в лаборатории защищённых информационных систем и магистерской диссертации. Март 2026 — стык: дисциплина закончилась, НИЛ ЗИС начался.

*17 февраля – 4 марта 2026*

Дисциплина началась не с алгоритмов, а с инфраструктуры: захотелось полностью контролировать формат, в котором потом работать. Написал свой парсер и пакер `BMP`, включая `RLE8` и `RLE4` — не потому что нужно, а чтобы разобраться, как устроены все пять ситуаций RLE-кодирования и где обычно ломается padding.

- **`BMP`-драйвер:** разобрал все шесть размеров DIB-заголовков (`BITMAPCOREHEADER`, `BITMAPINFOHEADER`, `V2`–`V5`), маски `BITFIELDS`/`ALPHABITFIELDS`, палитры, top-down/bottom-up ориентацию. Кодеры возвращают только индексную карту, а палитра применяется в драйвере — чтобы `RLE8`/`RLE4` не применяли её дважды.
- **`RLE8`/`RLE4`:** реализовал все пять ситуаций — run-length, `EOL`, `EOF`, delta-прыжки и absolute-контейнеры. Для `RLE4` отдельно обработал чередующийся паттерн `ABAB...` и padding nibble-последовательностей. Написал генератор сложных растров из пяти типов строк и прогнал 256 раундов тестов — `RLE8` и `RLE4` сходятся на всех.
- **Квантование и палитры:** реализовал дизеринг через `numpy` — `advanced indexing` + `broadcasting` + вычитание + `argmin`, без циклов. Режимы `mono`, `cga16`, `gray16`, `random`, `random2` — от терминальной палитры `Pascal GUI` до случайной палитры, которая сохраняет только яркости, но мозг всё равно читает сцену.
- **`DICOM` → `BMP`:** конвертер медицинских снимков в grayscale `512×512` с `RLE8`-сжатием и упаковкой в `BZIP2`. `BZIP2` на индексной карте дал 9.57 МБ против 10.3 МБ у `LZMA` — из-за `BWT`, который любит локальные корреляции.

*5 – 24 марта 2026*

Поверх готового `BMP`-стека — `LSB`-стеганография, метрики и GUI. Здесь же появились `PSNR`, `SSIM` и доверительные интервалы, которые потом перейдут в магистерскую диссертацию.

- **`LSB`-встраивание:** реализовал `get_k_layer`, `insert_k_layer`, `read_k_layer` с длиной сообщения в последних 32 битах. Векторизовал всё через `numpy` — `unpackbits`, маски, сдвиги.
- **Метрики:** `MSE`, `PSNR`, `SSIM` — с нуля, без `scipy`. Для `PSNR` отдельно обработал случай `MSE = 0` (`inf`), для `SSIM` — константы `C1`/`C2` и ковариацию через `numpy.var`/`mean`.
- **Доверительные интервалы:** аппроксимация обратной CDF нормального распределения по методу Акклама, без `scipy`. Для `n = 100` и `α = 0.05` даёт `z ≈ 1.96`, но работает и для других `α`.
- **GUI на `Tkinter`:** `ScrollableFrame` с двумя ползунками (5 часов боли), `ResizableTextFrame` с `size-grip`, `ControlPanel` с декларативной системой конфигурации (`FDDSCS`). Отдельно — `ImageGridBase` для сеток картинок и `HistogramGUI` с асинхронной генерацией гистограмм через `ThreadPoolExecutor`.
- **Анализ битовых плоскостей:** визуализация `k=1…8`, `MSE`/`PSNR`/`SSIM` для каждой плоскости, гистограммы и доверительные интервалы по трём наборам (`BOSSbase`, `medical`, `portrait`). Подтвердил теоретический потолок дисперсии `0.25` для бинарных плоскостей.

*29 марта – 11 апреля 2026*

Цифровые водяные знаки: `LSB` с ключом и адаптивный метод по локальному градиенту. Здесь же выяснилось, что `argsort` в `blind`-режиме не работает — и это не баг, а свойство метода.

- **`LSB` с ключом:** генератор последовательностей поверх произвольной `unicode`-строки через `PBKDF2-HMAC-SHA256` → `SeedSequence` → `PCG64`. Пароль влияет на перестановку индексов так же, как вход `SHA-256` на выход — подобрать без раундов `PBKDF2` нереально.
- **Адаптивный метод:** девять градиентных ядер (`diff`, `central`, `scharr3`, `prewitt3/5`, `sobel3/5/7`, `roberts`), свёртка через `numpy` с поддержкой `valid`/`same`, нормализация в `[0, 1]`. Логотип автоматически уменьшается через `LANCZOS` до размера слоя.
- **`Non-blind`:** выяснил, что `argsort` по градиенту требует оригинал — иначе перестановка индексов ломается уже на восьмом элементе. Это не недостаток, а свойство: `non-blind` адаптивный метод даёт карту изменений, которую нельзя подделать без знания ядра, ключа и параметров сортировки.
- **Результаты:** `LSB` проваливается по `PSNR` на всех трёх наборах, адаптивные методы дают стабильно более высокое качество — разница систематическая и видна даже по узким доверительным интервалам.

*2 – 7 мая 2026*

Обратимая стеганография: `Histogram Shifting` (`Ni et al. 2004`, `Ni et al. 2006`) и метод Кима на разностных диаграммах субсемплов. Самая тяжёлая часть — не алгоритмы, а отладка обратимости.

- **`Ni et al. 2006`:** реализовал все семь шагов — поиск трёх zero-points, локальные пики в интервалах, `top2_in_interval`, `refine_peak`, fallback на `Ni et al. 2004`, если все три пика `None`. Ёмкость выросла в десятки раз за счёт выбора `HeapSort` вместо `QuickSort` внутри `argsort` — более удалённые нулевые бины дают больше пар.
- **Проблема недетерминированного `argsort`:** `np.argsort` с `kind='quicksort'` даёт разные перестановки нулей на разных машинах. Решил через `stable_argsort` с явным `rng.choice` по кандидатам — детерминированно, но с сохранением псевдослучайности.
- **Симулятор не работает:** пытался предсказать обратимость по гистограмме и парам — эвристики и структурные симуляторы дают `OK` там, где реальный `embed`/`extract` даёт `False`. Причина: гистограмма не содержит порядка пикселей и реального `payload`. Единственный надёжный способ — реальный прогон.
- **Три бага, которые стоили часов:** `UNDO SHIFT` без `>=` (хвостик `946` не сдвигался между `hist[16]` и `hist[17]`), пустая пара в `bits_per_pair` (размер первой пары попадал в последнюю при обратном обходе), и пиксели `0`/`255` (после встраивания бита дают `-1`/`256`, нужно сжимать диапазон на `L+1` с обеих сторон).
- **Метод Кима:** субдискретизация на тайлы, опорный тайл, разностные изображения, сдвиг гистограмм разностей. Проблема `512` не делится на `3` — обойти нельзя, обрезка после `embed` разрушает структуру тайлов. Для `(du, dv) = (2, 2)` при `PSNR ≥ 40 дБ` ёмкость `~100 кбит` на `BOSSbase`, `~129 кбит` на `medical` — в 4–6 раз больше, чем у `HS`, при сопоставимом качестве.

### Исследование линейной хэш-функции в `RDH`-стеганографии (НИЛ ЗИС)
*7 – 8 мая 2026*

Первый заход в дипломную тему — и сразу два закрытых зачёта: учебная практика и научно-исследовательская. Формально отзыв по практике не требовал программы, но без неё было не понять, что именно делает `StegoHash` и как оценивать его применимость. Когда код появился, он сам закрыл оставшиеся пункты исследования.

- **Порт `StegoHash` с C++ на Python:** переписал `BitStr`, `DiscrLog`, `Lambda`, `StegoContainer`. Вместо массива `char` с одним битом на символ — целое число `int` и `__slots__`. `XOR` и полиномиальное деление над `GF(2)` теперь работают на лимбах CPython (30 или 60 бит за операцию) вместо посимвольных циклов — на порядок меньше итераций на длинных контейнерах.
- **Семантическая совместимость:** реализовал `__int__`, `__index__`, `__format__`, `__add__`, `__mod__`, `__len__`, `__getitem__`. `BitStr` работает в `range`, срезах, `f`-строках и как аргумент операторов — без адаптеров, что упрощает интеграцию с `Pillow`/`OpenCV` на следующих этапах.
- **Тесты:** переписал все C++-тесты на Python, плюс исчерпывающий эксперимент: при `capacity = 7` перебрал все `2^7 = 128` контейнеров и все сообщения. Корректность извлечения и идемпотентность сошлись без исключений.
- **Главный вывод:** схема Рябко–Фионова не является `RDH`. При `capacity = 2` контейнеры `00` и `01` при сообщении `0` дают одинаковый `stego` `00` — отображение не инъективно, исходный контейнер не восстановить. Это не баг, а свойство: схема решает задачу оптимального встраивания, но не задачу восстановления контейнера.
- **Литературный обзор:** разобрал `Paris2019` (Рябко и Фионов, линейная хэш-функция), `AMHM` (He et al., 2021, TIFS), `Dual Pairwise PEE` (He & Cai, 2021, TIP), `Daiyrbayeva et al.` (2025, медицинские изображения). Выделил системную проблему: `PSNR`/ёмкость оптимизируются, а статистическая скрытность — нет.
- **Дальнейшие телодвижения:** соединить линейную хэш-функцию с интерполяционным `RDH` — как в `Daiyrbayeva et al.`. Исходные пиксели остаются нетронутыми (обратимость), интерполированные — пространство для встраивания, которым управляет `λ`. **Аналогия** — `sampler2D` в `OpenGL`: он весь построен на интерполяции между текселями и при этом не обязывает, но и не запрещает попадать точно в центр текселя; в интерполяционном `RDH` каждый четвёртый пиксель ложится ровно на оригинальный (целые координаты), а остальные ¾ — в дробные, где и живёт встраивание.

### Моделирование
*11 – 22 мая 2026*

По заданию двухканальной СМО нужно было построить и исследовать модель в `AnyLogic`, но по согласованию с преподавателем я написал свой дискретно-событийный движок на Python. Причина простая: `AnyLogic` — это готовая среда, а хотелось разобраться, как устроен планировщик событий, очередь и блоки обслуживания изнутри, а не собирать схему мышкой.

- **`EventEngine` на `SortedList`:** события хранятся как кортеж `(time, counter, callback, payload)`. `SortedList` даёт `O(log n)` на вставку и извлечение, а `counter` разрешает коллизии событий с одинаковым временем — иначе компаратор добрался бы до `callback` и упал. `run(until)` возвращает событие обратно в очередь, если оно за пределами окна, чтобы движок можно было переиспользовать.
- **Блоки на `__slots__`:** `Job`, `Sensor`, `ServiceDevice`, `TupleCombiner`, `RandomOutput`, `Sink`. У каждого — свой набор полей и минимум методов, чтобы на длинных прогонах (10 000+ событий) не тратить память на `__dict__`. `Job` умеет разворачивать вложенные `Job` в плоский кортеж — это нужно, когда пара от `TupleCombiner` попадает в `Sink`.
- **`Sensor`:** пуассоновский генератор с `τ = 1/λ`, `exponential` через `-log(U)/λ`. Поддерживает группы: если `group is not None`, сенсор не стартует сам, а ждёт `Sensor.start(group)` — это позволяет синхронно запустить несколько потоков после сборки схемы.
- **`ServiceDevice`:** два режима — `uniform` (`E[S] = (a+b)/2`) и `exponential` (`E[S] = 1/μ`). Считает `accepted`, `finished`, `|queue|`, `E[S]`, `μ`, `λ`, `ρ = λ/μ` — прямо в `stats()`, с проверкой `accepted == queue_length + finished`.
- **`TupleCombiner`:** собирает по одному `Job` от каждого входа и выдаёт пару. Внутри — `deque` на каждый вход и счётчик пустых буферов, чтобы не проверять все буферы на каждом `accept`.
- **`Builder`:** декларативная сборка схемы с `__getattr__` — `b.sd1` вместо `b["sd1"]`. `run_with_logging` через `exec` генерирует функцию логгера под конкретный набор блоков и свойств, чтобы не писать `getattr` в цикле на каждом шаге.

**Курсовая.** Вариант 3: двухканальная СМО с двумя пуассоновскими потоками (`λ = 1.0` и `λ = 1.25`), общей очередью и равномерным обслуживанием `σ₁ ∈ [0.5, 1.4]`, `σ₂ ∈ [0.7, 1.4]`. Задача — распределение интервалов между выходами пар из `Sink`.

- **Граф событий:** `E1`–`E8` от прихода до выхода пары. Проверил по правилам: приоритеты не нужны (комбинатор сработает после обоих приходов), редукция `E2`/`E3` невозможна (`σ > 0`, `O2` входит в условие на дуге), инициализация — два независимых сенсора.
- **Аномалия:** `ρ(sd2) = 1.32` — второй канал перегружен, его буфер забивается, а первый канал `ρ(sd1) = 0.94` простаивает. В `TupleCombiner` это видно по `buffers = (647, 0)` — первый буфер растёт, второй пуст. Пара выходит только когда есть оба `Job`, значит `Sink` получает 9529 пар, а не 10176.
- **Два решения и почему оба не идеальны:** понизить поток второго сенсора (`τ: 0.8 → 1.056`) — решает перегрузку `sd2`, но не переполнение буфера `tc1`. Повысить пропускную способность `sd2` (уменьшить `σ₂`) — усугубляет разрыв между каналами. Единственный способ убрать простой комбинатора — выровнять `E[S]` у обоих каналов, а потом уже понижать `τ₂`.

*16 – 23 мая 2026*

Продолжение дисциплины первого семестра, но с уклоном в моделирование и машинное обучение. Пять лабораторных — от точной задачи коммивояжёра до нейросети, которая должна распознавать лица. *16 – 21 мая 2026*

- **TSP:** полный перебор через `itertools.permutations` с векторизованным подсчётом длины через `numpy` — `dist[path[:-1], path[1:]].sum()`. Для `n ≤ 10` работает, для `n = 15` уже нет.
- **Хелд–Карп:** динамика по маскам, `dp[mask][last]`, `O(n² · 2ⁿ)`. Восстановление пути обратным ходом — ищем `prev`, для которого `dp[prev_mask][prev] + dist[prev][last] == dp[mask][last]`.
- **Бенчмарки:** `time.perf_counter` (монотонный, не привязан к системным часам), графики в `matplotlib` — линейный и логарифмический, плюс отношение времён `T_brute / T_dp`.

*21 – 22 мая 2026*

- **Многозадачность:** симулятор планировщика с приоритетным вероятностным выбором. `Weights` строит `pool` повторением индексов пропорционально приоритетам, `choose_one()` — случайный выбор, `choose_k_without_replacement()` — через `random.sample(..., counts=...)`.
- **Аномалия:** при `cores ≥ 4` писатель блокирует доступ к читателям всегда, при меньшем числе ядер — только с вероятностью. Лучшая производительность, когда число прочитанных и записанных символов за квант сходится и равно числу логических ядер.
- **Бюффон:** `buffon_trial` через два `uniform`, отклонение `Δ = |P_exp - P_theor| / P_theor`. На логарифмическом графике `Δ(N)` — прямая с наклоном `~ -1/4`, что соответствует `1/√N`. На `N < 100` колебания сильные, на `N = 120` уже видно, что `Δ` может быть больше при большем `N` — это не баг, а дисперсия.

*22 мая 2026*

### Сетевые базы данных (PostgreSQL)
*6 августа – 26 сентября 2026*

Дисциплина построена вокруг `PostgreSQL` 18.4 в `Docker`: не «поставил и забыл», а «развернул с безопасной передачей секретов, разобрался с метаданными, потом уже запросы». Задания были написаны под `Oracle`, поэтому каждый раз приходилось переписывать `DDL` и `DML` под `psql` — с переносом всех `ALTER` внутрь `CREATE TABLE`, заменой `SET DEFINE OFF` и `REM` на `psql`-эквиваленты.

*6 – 7 августа 2026*

- **Docker:** развернул `PostgreSQL` 18.4 с `POSTGRES_USER_FILE` и `POSTGRES_PASSWORD_FILE` вместо пароля в `-e`, с `scram-sha-256` и томом `my-pgdata`. Отдельно разобрался, почему в 18+ монтируется не `/var/lib/postgresql/data`, а весь `/var/lib/postgresql` целиком — иначе `pg_upgrade` не сможет работать из-за границы монтирования.
- **Метаданные:** `\d+`, `\dT+`, `\df+`, `\sf+` — разобрался, как `SERIAL` превращается в `DEFAULT nextval(...)`, где живут `CHECK`-ограничения, и почему `pg_roles` — это `view` на `pg_authid` со скрытым паролем и добавленным `rolconfig`. `rolconfig` дублирует настройки роли, но только глобальные (`setdatabase = 0::oid`).
- **Триггер на `plpgsql`:** для инвентаря из `Dismantle` — ограничение числа слотов и размера слота, с удвоением для редкости при наличии компрессора. `CHECK` не умеет смотреть в другие таблицы, поэтому логика ушла в `BEFORE INSERT OR UPDATE`-триггер.

*14 – 16 сентября 2026*

- **Коррелированные подзапросы:** пять заданий по два запроса — через `ANY`/`ALL`/`EXISTS` и через `JOIN`. Для каждого — `EXPLAIN ANALYZE` и разбор, когда `SubPlan` декоррелируется в `Hash Semi Join`, а когда остаётся `SubPlan`.
- **Планы:** `InitPlan` — для некоррелированных подзапросов, `SubPlan` — для коррелированных. `shared hit` — это `mmap(MAP_SHARED)` из Linux, общий буферный пул для всех backend'ов. Сравнение `MAX` и `ALL` на маленькой БД дало разные планы, но одинаковый результат.
- **`WITH RECURSIVE`:** иерархия организаций из `CORP.sql` — якорь (каждый узел корень своего поддерева) + рекурсия (дети через `crp_pid`), потом `SUM` по `GROUP BY`. `LIMIT 1` превращает `quicksort` в `top-N heapsort`, но `CTE` остаётся отдельным блоком плана и не встраивается в дерево.
- **Оконные функции:** `PARTITION BY` даёт первичную сортировку, которую `Incremental Sort` переиспользует через `Presorted Key`. `RANK` вместо `ROW_NUMBER` — чтобы при одинаковом числе голов не терять игроков из-за порядка в таблице. `Run Condition` в `PostgreSQL` 18 проталкивает `rn <= 3` внутрь `WindowAgg`, и строки с `rn > 3` вообще не обрабатываются.
- **`convert_inserts.py`:** написал скрипт для `wc2014.sql` — 116 `INSERT`-ов в один `multi-row`, с выравниванием столбцов через `ljust`/`rjust` и сортировкой по первому столбцу. Вручную это заняло бы вечность.

*25 – 26 сентября 2026*

- **Динамический `SQL`:** процедура `print_sal_v3` с `format('%L')` для значений и `format('%I')` для идентификаторов. `concat_ws` вместо `||`, потому что `NULL` «отравляет» цепочку `||`, а `concat_ws` пропускает `NULL` и ставит разделитель только между непустыми. Массивы в `PostgreSQL` иммутабельны — `array_append` возвращает новый массив, так что `O(n²)` никуда не делся.
- **`RAISE`:** `NOTICE`/`WARNING` — вывод в `stderr`, не прерывают. `EXCEPTION` — прерывает, откатывает транзакцию, пробрасывает наверх (аналог `throw`). `\set ON_ERROR_STOP on` — аналог `set -e` в `bash`, но только на уровне `psql`, не процедуры.
- **`SQL`-инъекции:** убрал валидацию `p_op` — и процедура стала уязвима, несмотря на `%L` для `p_sname`/`p_city`. Комментарий `--` обходит `WHERE`, `pg_sleep(3600)` даёт `DoS`, `generate_series(1, 1e9)` с `ORDER BY random()` — `CPU`-атаку с spill на диск. 100 параллельных клиентов забили `max_connections = 100` — `FATAL: sorry, too many clients already`.
- **Лечение:** `pkill -TERM -f "postgres: admin labs"` — корректное завершение backend'ов, каждый откатил транзакцию и освободил слот. `pkill` клиентов не убивает backend'ы: `psql` — это клиент, backend — отдельный процесс. `DROP PROCEDURE print_sal_v333(text, text, text)` — с сигнатурой, потому что `PostgreSQL` поддерживает перегрузку, но хранит типы в `pg_proc`, а не в mangled-имени, как `C++`.

### Перспективные технологии защиты информации
*26 сентября – 15 октября 2026*

Последняя дисциплина — и, пожалуй, самая «инженерная»: собрать с нуля полную цепочку сквозного шифрования, от генератора простых чисел до GUI-чата, где сервер не знает ключа. Не «взять `cryptography` и обернуть», а реализовать `DH`, `MQV` и `Sosemanuk` так, чтобы они побайтово совпали с референсами.

*26 – 29 сентября 2026*

- **Порт `BigInteger` из OpenJDK:** `primes.py` — `Miller-Rabin`, `Lucas-Lehmer`, символ Якоби, сегментированное `BitSieve`. Решето отсеивает кандидатов по малым простым до дорогого `pow`, оставляя ~12% на полный тест. `test_primes.py` — порт `PrimeTest.java`: 100 001 известное простое, 10 000 случайных не-простых, простые Мерсенна до `2^3217 - 1`.
- **Профилирование `pow`:** `probable_prime(4096)` — 96.2% времени уходит в `builtins.pow`, 3.5% — в `Lucas-Lehmer`, 0.3% — в решето. Написал `modpow_mont` с окном 4 и инлайн `redc` — теоретически быстрее, на практике медленнее (15.6 с против 9.2 с у `pow`): интерпретатор и boxing съедают весь выигрыш от Montgomery. Это не повод бросать оптимизацию, а повод понять, где именно она умирает — в Python каждая лишняя операция стоит дороже, чем экономит алгоритм.
- **`gmpy2` как прагматичный ход:** вместо того чтобы тащить `modpow_mont` в `Cython` и всё равно проигрывать, подключил `gmpy2` — `pow` ускорился в 10.5 раз, `mpz` работает как drop-in для `int` (включая `pow(a, -1, m)` через расширенный Евклид). Это не «сдался и взял библиотеку», а «понял, где интерпретатор съедает выигрыш, и выбрал правильный инструмент»: своя реализация осталась как эталон и доказательство, что алгоритм понят, а рабочая версия — на `GMP`.
- **`DH` и `MQV`:** `gen_safe_prime` (p = 2q + 1) против `gen_subgroup_params` (p = t·q + 1). Подгруппа быстрее при той же стойкости: `q` генерируется один раз, а не тысячи, пока `2q+1` не станет простым. `MQV` — коэффициенты `d`, `e` из младших `l` бит `X`, `Y`, секрет `S = (Y·B^e)^(x+da) mod p`, ключ `K = sha256(S)`. В `safe prime` пришлось возводить `g` в квадрат: формулы `MQV` выведены для подгруппы порядка `q`, иначе `S_A ≠ S_B` с вероятностью ~50%.

*30 сентября – 13 октября 2026*

- **Транспорт:** `codec.py` из `jni_rpc` — `ULEB128`, `SLEB128`, `bigint`, `shorty`-оптимизированный `args_writer_gen`. TCP-сервер с комнатами, `push` через `wlock`, `push_messages` батчем, `Room.history` — `deque(maxlen=1000)`. Timeout на сокеты — чтобы `Ctrl+C` выбирался из системной блокировки.
- **`Sosemanuk`:** полный порт — `Serpent24` key schedule (`WUP0`/`WUP1`, 25 шагов `SKS`), bitslice `S`-боксы Оsvik, `LFSR`/`FSM` (`_step`, `_srd`), `MUL_A`/`MUL_G` через таблицы. Верификация — `DTV_digest` (SHA-256 всего трейса) совпал с `TEST_VECTOR_128.txt` побайтово.
- **GUI:** `tkinter` — `Canvas` + `chat`-фрейм, пузыри свои/чужие, палитра Telegram Light, цвет ника через `SHA-256(uid)`. `Ctrl+C/V/X/A` через `keycode`, а не `keysym` — не зависит от раскладки.

*14 – 15 октября 2026*

- **E2EE:** `room_crypto` — `PBKDF2-HMAC-SHA256` (100k итераций), verifier `data || sha256(data)` (224 + 32 байта), шифруется `Sosemanuk`. Сервер хранит `salt` и `verifier`, но не ключ. `proof-of-knowledge`: клиент присылает `sha256(pt_v)`, сервер сверяет с сохранённым — соврать про «я проверил пароль» больше нельзя, а сервер по прежнему не знает ключ.
- **Файлы:** `blob-store` — `uuid = os.urandom(16)`, в историю уходят метаданные + `uuid`, содержимое по запросу. `fetch_blob` — асинхронный с `_blob_waiters` и таймаутом. GUI — кнопка 📎, лимит 5 МиБ, клик по файлу — диалог сохранения.
- **Профилирование:** `profiling.py` — `measure()` как контекстный менеджер, `PROFILING=1` включает, `atexit` дампит. Замеры: `PBKDF2` 55 мс, `Serpent24` schedule 0.144 мс, сообщение 0.4 мс, файл 4 МиБ — 1.8 с.
- **Оптимизация `Sosemanuk`:** кеш `_STEP_INDICES`/`_SRD_BASES` (убраны 9 `%` на `_step`), inline `MUL_A`/`MUL_G`, раскрытие циклов, `pack("<IIII")` вместо четырёх `to_bytes`, `b"".join`, `map(operator.xor)`. Шифрование 4.12 МиБ: 2.99 с → 1.78 с (`×1.68`), `crypto.xor`: 323 мс → 125 мс (`×2.58`). Верификация по `eSTREAM` не сломалась.
